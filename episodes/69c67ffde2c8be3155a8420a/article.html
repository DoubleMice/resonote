数据角度看 OpenClaw 的企业落地

嘉宾：刘华阳，企业数据库架构师；戴涛，OceanBase AI 解决方案负责人

来源：屠龙之术 · 发布：2026 年 3 月

AI 产品技术战略圆桌

OpenClaw 的热度，先来自一个很具体的想象：给它授权、交代任务，一个能搜索、写作、调用工具的个人助手就开始替人做事。本期对谈没有从模型能力切入，而是把镜头移到企业的数据层。刘华阳和戴涛关心的是同一个问题：当这类 Agent 不再只服务一位用户，而要接入企业的文档、系统和流程时，底下那层数据与控制机制够不够用。

两人并不否认个人场景的吸引力。戴涛认为，OpenClaw 的起点就是个人助理，用户可以在自己的设备或云端环境中决定开哪些权限。企业想要的东西不同：它希望把员工经验沉淀下来，在一定范围内承担重复工作，或让现有员工完成原来做不到的任务。这样的数字员工会碰到更多数据源，也要面对谁有权调用、谁对结果负责的问题。

个人授权不能直接搬进企业

讨论一开始就落在安全边界上。戴涛提到，他曾在客户面前测试一套 OpenClaw 部署，询问 token 放在哪里后，系统直接给出了结果。这个例子不说明所有部署都会泄露凭据，却说明企业不能把个人场景中方便的默认授权照搬过来。刘华阳也说，自己的团队不在办公电脑上部署这类工具，而是在云端或独立设备上做探索。

难点不只是一把 token。企业里少则七八套系统，多则数百上千套；即使只开放一台电脑或一个 IP 的权限，也会牵动内部控制。数据一旦参与任务，企业还要知道它保存在哪里、谁看过、是否被修改，以及能否留下审核记录。对个人用户而言，Markdown 文件可能是一种足够直观的记忆载体；对企业而言，文件的位置、访问范围和保留期限都属于架构的一部分。

敏感数据凭据、文件和业务记录不能因为智能体需要工具就默认暴露。
权限边界Agent 接入的每个系统都要明确可读、可写和可执行的范围。
审计能力企业需要追溯数据与操作，这也是把个人工具改造成企业服务的条件。

AI 会把数据孤岛问题重新带回来

刘华阳想起大数据建设早期的困境：数据要反复传输、清洗、汇总，可能出现缺失、不及时或不一致；同一份数据落在不同副本和工具中，成本不断堆高。后来架构收敛，问题才逐渐可控。他担心，AI 应用如果继续按项目各自部署向量库、RAG、Agent 框架和处理管线，企业会再次面对类似的复杂度。

戴涛的观察与此相接。国内企业在近两年已经尝试多套 Agent 和 RAG，既有开源组件，也有厂商部署版本。早期试验时，各自带一套框架并不显得严重；当应用变多，底层数据库、切分方式、存储结构和调用接口互不相同时，维护和治理就会变成共同问题。对谈中提到的 AI 中台、统一技术栈或统一数据底座，都是在回应这种分裂，而不是给某一个产品换个名字。

先试用与先治理可以并行
戴涛没有主张企业必须把数据治理全部做完才开始 AI 项目。他提出的节奏是先在知识库、营销生成或某个业务域完成局部试点，再扩展到主要业务板块；应用规模上来后，再集中处理共享能力、数据底座与治理。

向量检索解决一部分搜索，不是全部数据架构

两位嘉宾对把支持向量功能的数据库直接称为 AI 数据库持保留态度。向量数据库本身并不是大模型时代才出现的技术，它把非结构化内容表示为高维空间中的点，用相似度寻找内容。大模型让语义搜索更可用，也让这项能力的应用范围扩大，但并没有把其他检索条件消掉。

节目用找餐厅的请求说明这一点：附近、适合约会、宠物友好、人不多、可以预订，既有语义判断，也有距离、可订状态等结构化条件。文本、图像、音频和视频进入企业系统后，问题还会变成多模态检索。嘉宾所说的混合搜索，指的就是让向量相似度、结构化筛选和其他数据处理共同服务一个请求，而不是只把一层向量索引外挂在原有系统上。

戴涛把理想中的底层称为 AI 数据湖库：文本、图像、音频、视频和业务字段在一个可共享的存储与处理基础上提供检索、实时访问、轻量分析和 API。这个说法是他提出的产品与架构方向，并不是节目用来证明行业已经形成统一标准的结论。它所针对的，是业务团队把需求直接交给 Agent 或 Web Coding 工具之后，底层是否还能避免按应用重复建设。

记忆要按内容和生命周期来设计

上下文窗口变长，并不等于 Agent 已经解决了记忆。戴涛认为，窗口会受到处理能力和 token 成本限制；若把长久历史一股脑交给模型，成本很快失控。从企业架构的角度，他倾向于让模型尽量保持无状态，把需要保存的信息交给外部的记忆方案。

节目区分了至少三类对象。企业文档、内部资料等知识性内容适合用 RAG 检索；用户的对话、偏好和个人经历属于交互记忆，需要区分长期与短期、私有与团队共享；固定的操作规程可以整理为 Skill，供 Agent 在特定任务中调用。它们可以共存，但不能因为都被称为记忆就使用同一种存储和检索方式。

刘华阳补充了企业数据管理中的时间难题。传统数据往往能规定保存三年或五年，到期清理；与用户长期互动的 AI 记忆却难以在建立时就确定删除时点。因此，外部记忆不是一张不断累积的聊天记录，还需要新增、检索、更新和淘汰机制。嘉宾提到，购物搜索可以保留此前的提问，健康助手可以记住用户上传的报告和过往问询；下一次回答时只取回相关信息，就不必再把全部历史对话塞进模型。

新增提取值得保留的事实、偏好或业务记录，而不是照单全收。
检索与更新按任务找回相关内容，并允许新信息补充或覆盖旧记录。
淘汰保留多久、谁能共享、何时删除，仍要由业务与合规要求决定。

Agent 作为入口，会放大控制层的重要性

主持人把 OpenClaw 想象成一个统一入口：搜索、企业制度查询、知识库、问数和编程任务都能从这里开始。这种入口的好处是用户不必记住每个系统在哪里；相应地，Agent 会接触更多账户、文件和内部服务。权限、审计、沙箱和数据存储不再是上线后补的外围功能，而会参与每一次工具调用。

戴涛介绍了 OceanBase 正在探索的方向：专业用户仍可把 SQL 作为基础语言，普通业务用户则通过中间件、知识库、Skill 或其他应用界面使用数据能力；需要管控的记忆和 SOP 可以放进可管理的存储，本地操作可以转入云上或内部沙箱。智能体访问数据和工具之前，需要经过可检查的边界；入口集中不意味着默认权限扩大。

企业部署的取舍
Agent 的价值来自连接数据、工具和行动；风险也沿着同一条链路扩大。能否把访问范围限制在授权资源内，并留下可追溯记录，决定了这类入口能否进入核心业务。

先从一处业务开始，再决定如何扩展

节目的最后没有给出一种包治百病的企业 AI 架构。刘华阳的底线是，使用 AI 前，数据至少要处于可治理的安全范围。戴涛则建议企业不要因为不确定而完全停下，但推进方式应当克制：先找到一个业务域，验证知识库、内容生成或提效任务能否解决真实问题；再把有效的做法扩大到更多场景，同时补上数据治理、共享存储和访问控制。

因此，OpenClaw 在这场讨论中更像一次压力测试。它让人看到模型已经能够连接任务和行动，也把企业原本分散处理的问题集中摆到台前：数据是否可靠，记忆怎样保存，系统如何授权，成本怎样控制，出错时又由谁追溯。企业落地并不取决于是否装上一个个人助手，而取决于这些基础问题能否随着使用范围一起被解决。
