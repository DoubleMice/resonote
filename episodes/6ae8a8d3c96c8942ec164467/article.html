61. 在Harvey训练大模型是什么体验？- Joey Wang

嘉宾：Joey Wang，Harvey 的 agents 与内部云端 AI 平台负责人

来源：《苔藓之火》

法律 AI 的工作流入口

法律 AI 必须进入 Word、邮件和文档系统，并把修改的来由留给律师审阅。

训练从评测开始

Harvey 依据贴近客户工作场景的评测，决定应当优化什么和采用哪种基座模型。

部署依赖边界

无论是法律 agent 还是内部协作 agent，权限、责任和可追溯性都决定了产品能否被信任。

Harvey 面向律所和企业法务提供法律 AI。Joey Wang 在节目中谈到，自己约三年前加入这家公司，早期做过历史记录与核心数据的接入；目前负责部分 agent 功能，以及公司内部的云端 AI 平台。他从 Uber、Figma 转到 Harvey，看重的是把想法做成产品、交给客户使用，并很快得到反馈的节奏。

法律领域的模型训练需要先让律师保留原有的审查方式，再把模型能力放进可复核的工作流；评测、数据和部署权限也都要围绕这件事安排。

律师已有的工作界面

Joey 认为，垂直产品首先要贴合客户已经在做的事。律师的日常并不只发生在一个聊天框里：合同常在 Microsoft Word 中修改，资料可能在 Excel 表格和文档系统中，协调工作又散在邮件里。Harvey 因此通过连接器接入邮件和文档系统，在原有材料上协助检索、起草或修改；模型输出的终点仍可能是一份 Word 文档。

保密协议是他用来说明差别的例子。一份 NDA 的审查包含针对条款的 playbook：哪些条款不能接受，哪些条款必须争取，哪些条件可以在谈判中让步。系统若能利用已获授权访问的工作数据，才有机会把这些判断放进后续流程；律师仍要决定哪些建议被采纳。

呈现方式同样重要。Harvey 会把建议做成 redline，也就是在文档中清楚标出删改和替换，并说明修改理由。律师应当能分辨某一处改动来自 Harvey、客户还是对方律师。Joey 把它比作工程中的代码审查：提交记录让人知道代码如何变化，法律文件也需要一条可审计的修改轨迹。导出给对方的版本中，律师确认采纳的 AI 修改会归到律师本人名下；未被采纳的建议则可以保留在审查记录里。

法律文件的风险不只在于生成结果是否通顺，还在于谁提出了什么改动、为什么提出、最终由谁接受。Harvey 的产品设计把这几层信息留在同一份审查过程里。

模型变强后，流程配置可以少一些

Harvey 与模型公司的关系从一开始就很近。Joey 回顾，创始团队曾用 GPT-3.5 演示完整的法律流程，再将结果与人工完成的工作比较；随后获得 GPT-4 的早期访问权限，并把产品卖给律所。随着模型迭代，团队一面使用新模型，一面向模型厂商反馈法律场景中的评测与优化方向。

这种迭代会淘汰一部分产品形态。Harvey 曾提供 Workflow Builder，让律师把反馈节点、文件上传、提示词、条件分支和最终文档写成固定流程。当时的 agent 容易忘记任务、漏要材料或在半途结束，因此需要懂流程的人把步骤编码出来。后来，团队把它转为 Agent Builder：用户给出提示词和所需的源文件或数据源，agent 可以直接交付结果。模型能力提高后，用户维护的显式步骤随之减少。

这也是他对通用模型会不会吞没垂直应用的回答。模型进步会让某些功能失去使用必要，但产品团队仍要理解模型的发展，并调整底层 AI 基础设施、输入资料和交付方式。对法律工作而言，模型能力只是其中一层；输出能否进入律师熟悉的审查与责任链条，仍是另一层问题。

后训练需要场景化评测

Harvey 早期已在做法律模型研究。Joey 说，在缺少足够数据时，预训练模型很难持续超过快速演进的通用模型；仅用有限数据做后训练，进步也可能赶不上 OpenAI、Anthropic 或 Gemini 的更新速度。后来，客户规模扩大带来了更多产品反馈，团队对法律使用场景的理解也变得更具体。

这里的数据并不等同于拿客户的私密材料训练。Joey 描述的做法是：从不涉及客户数据或隐私的反馈中归纳场景，再用这些场景构建 benchmark 和合成数据。团队由此评估不同模型，也为后训练寻找质量、成本和延迟之间的平衡。能否做出有价值的数据，取决于团队是否知道哪些细节能反映律师每天的真实工作。

他把这种判断称为对数据的 taste。通用写作任务里，简短常被当成优点；但法律客户有时需要很长的解释，并要求每一句都能追溯到来源。只奖励一句话概括的评测，即使让模型获得高分，也未必适合律师。垂直产品的团队需要让自身判断与客户判断相交，才能避免追逐脱离场景的通用分数。

从稳定任务起步

NDA 的 playbook 可以写成条件明确的判断，用较稳定、可重复的任务先校准评测。

让法律经验进入规则

内部法律团队持续审阅合同和 redline；他们的判断与更多领域专家一起丰富评测标准。

随使用场景更新

团队会把尚未完全确定的场景加入测试，并用 shadow run 或 A/B 测试核对用户实际反应。

法律没有一个覆盖所有问题的唯一标准答案，所以 Harvey 从可以回答是或否、能根据 playbook 判断的工作入手，再逐渐让更多法律人士的经验进入 rubric。规模扩大时，外部合作方可以帮助寻找标注或评分的人才；该评什么、前几十个样本是否合理，Joey 认为仍应留在内部。模型上线后客户不买账，团队会回到数据集和评测设计继续修改。

为每项任务选择模型基线

Harvey 的模型选择并不以厂商名气、参数量或单一价格为起点，而是看一个基座模型在某个具体评测场景中的表现。Joey 介绍，团队倾向于针对不同任务选择表现较好的开源模型，再做后训练或微调；需要批量处理、但不需要最高推理能力的环节，选择标准也会不同。

这会形成多个擅长不同任务的模型。Joey 用公司的分工打比方：一个更强的 agent 可以承担调度，把子任务交给适合的专业模型，再把结果组织起来。在他的设想中，用户把任务交给前台式的调度层，由它找到相应的模型完成工作。

客户的合规偏好也是模型选择的一部分。Harvey 同时提供多家模型厂商的选项，有客户不能使用某一家的模型，也有人要求默认使用 Claude。Joey 提到，如果客户选择 Claude，需要接受 Anthropic 按双方政策保留数据 30 天的条件。Harvey 不在中间额外过滤模型选择，而是争取所需的访问能力和容量，并处理可靠性与性能。

环节 团队要回答的问题
评测 这个任务的好结果，是否符合律师在实际工作中的判断？
后训练 选定基座模型后，能否在质量、成本、延迟和可靠性之间取得可用平衡？
部署 客户能否接受相应的数据政策，并在自己的权限与流程内使用结果？

Joey 还特别区分了研究结果和已交付的产品。训练未必第一次就超过原先使用的通用模型；有些尝试会失败，得分也可能更低。团队会先用评测找到某个法律场景下能力足够强的开源基座，把它当成进一步训练的起点。即使一次训练不部署给用户，过程中得到的评测与数据经验仍能用于下一轮。是否发布仍以用户是否愿意使用为准。

工程改善往往比换模型更快被用户感知

如果资源有限，Joey 目前会优先投资用户能立即感到的工程改进。模型训练是长期过程，而检索、并发和上下文组织常有更直接的回报。他举了文档搜索的例子：若一次搜索从两秒降到两百毫秒，在用户希望了解全部法律文件的一分钟内，agent 能检索的文件数可从约三十份增至约三百份；再把单文件搜索变成十路并行，规模可进一步到约三千份。模型不变，能看到的材料变多，结果就可能不同。

模型研究还会影响更长时间尺度上的成本和利润率。Joey 认为，模型能力、推理成本和利润率都会影响一家公司未来能否形成可持续的业务；但对尚在早期的创业公司，先把产品工程做好，往往比立刻投入自训模型更接近客户反馈。他也没有透露 Harvey 自有模型在调用量中的具体比例，只说用户仍可以按自身偏好选择模型。

人才结构也沿着同一逻辑变化。Harvey 早期一度缺产品经理和设计师；后来做模型时，增加研究人力也未必能解决瓶颈。懂专业领域的人要能够和研究人员一起定义验证方式。Joey 说，公司里的法律人士甚至会借助 coding agent 编写部分评测与评估工具，因为他们更清楚哪些结果对、哪些结果错；研究人员的工作是帮助这些判断被准确地提炼和实现。

内部协作 agent 需要清楚的权限边界

在法律产品之外，Joey 也做过一个供公司内部使用的云端 agent 原型。它把常见的 coding agent 放入沙盒运行，目的是让任务不再受个人电脑的硬件限制，并让多人在同一个运行上下文中协作。与其让几位工程师分别在本地跑同一问题、再交换一堆难以复核的结果，团队可以把不同意见放进共享的上下文，由 agent 汇总过程和结果。

实现这个想法的难点不在于把 agent 接进 Slack，而在于信息边界。一个 agent 需要知道发起请求的人有什么权限、当前频道是公开还是私有、它能查哪些信息、能对谁展示结果。代码流程也有既定约束，例如每一处代码需要两人审阅才能进入生产环境；agent 不应绕过这些约束，更不能让一个人借助别人的 agent 修改并提交代码。

因此，团队需要与安全和 IT 部门一起界定可开放的数据和规则，并让每个新 agent 读取这些约束。Joey 的判断是，用户只有相信私密对话不会被不该看到的人获取，才会愿意把工作信息交给 agent。熟悉的 coding agent 工具也有助于建立这种信任，但工具本身并不能替代权限设计。

中小律所市场的责任边界

访谈最后谈到中小律所。Joey 说，Harvey 在乎这部分市场；小律所需要的功能却未必正好是 Harvey 已有的功能。法律软件里谁对结果负责也不总能被用户清楚区分。编程 agent 的用户通常知道自己要对代码负责，法律 agent 的用户却可能过度相信系统，进而认为服务商应为结论承担责任。

这使 Harvey 更看重合适的 design partner。合作方需要有自己的管理规则，能够正确使用、审查并管理 AI 参与后的结果；双方也要在数据和责任边界上建立信任。法律客户长期采用这类产品，需要真实工作流、可验证标准和明确权限同时成立。
