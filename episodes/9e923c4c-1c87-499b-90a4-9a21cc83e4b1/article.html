一个催发货 AI 要跑通 260 步：和彭新宇聊中国式 FDE

嘉宾：彭新宇，阿里巴巴集团副总裁、瓴羊 CEO

为什么这期值得关注

一个电话，260 多步

催发货要穿过订单、仓库和多个电商平台，客服解决问题的能力取决于后端流程是否连得起来。

FDE 的三种能力

AI 锐度、行业深度和数据宽度共同决定 Agent 能否按业务目标工作。

AI 实施像招员工

企业要给数字员工权限、目标和裁量权，还要在上岗后持续复盘。

标准化与个性化

平台提供共性环境，企业数据和岗位标杆决定最后的工作方式。

先算结果，再选模型

坐席费、效果费、模型成本和数据治理都要放进同一本账里。

从 C 端热闹到 B 端账本

主持人在开场提出一个企业软件市场的老规律：客户每花 1 美元购买软件，还要再花 6 美元把它用起来。AI 正在重新分配这部分投入，企业软件的价值因此要回到使用结果上判断。

彭新宇把瓴羊描述为企业级增长 Agent。它围绕消费流通场景工作，覆盖营销、销售、客服和运营。个人用户会追求新奇体验，企业则要找到重复工作，比较投入、效率和业务结果。

这场对话的重点不在于给 FDE 添加一个更时髦的解释，而在于把岗位放回企业现场：流程有多长，数据是否可用，谁拥有权限，结果怎样验收。

作者概括：企业级 AI 的关键问题，已经从模型能否展示能力，转向企业能否把能力放进一条可衡量的工作流程。

FDE 的溢价来自能力组合

彭新宇认为，企业不会因为职位换名就多付钱。FDE 的稀缺性来自三种能力同时出现：它要有 AI 锐度，理解模型与工具；要有行业深度，理解业务流程；还要有数据宽度，能够治理企业数据和上下文。

传统运维首先保证系统正常运行。FDE 还要判断系统是否沿着业务目标变好，哪里需要调整技能、数据上下文、记忆或权限。这项工作要求运维人员理解业务，也要求业务人员能读懂数据和 Agent 的行为。

因此，FDE 和驻场运维的分界点不在地点，而在责任对象。前者要对业务结果负责，后者主要对系统状态负责。

交付对象从功能变成业务结果

彭新宇把企业级 Agent 的实施拆成三个前提。第一，企业要先找到具体问题，并为它建立业务数字、历史记录和测评集。第二，企业要把数据、权限和上下文整理成 Agent 能使用的基础。第三，企业要把岗位标杆设为 Agent 的起点。

岗位标杆可以是最佳客服、最佳投手或最佳销售。它应该指向企业里真实存在、可以被观察和比较的工作方法，而不是一段空泛的人设。Agent 进入企业后，要沿着这个参照系工作，再根据结果调整。

企业验收的对象也随之改变。系统能不能交付只是开始，成本是否下降、处理效率是否提高、销售或营销是否产生增长，才决定这项服务是否有价值。

260 多步催发货，暴露了企业真正的难题

催发货不是一个单一问题。客户可能只收到一台空调，可能缺少配件，也可能没有收到承诺的赠品。客服接到电话后，要核查订单、库房、派单和发货状态，还要在企业内部系统与外部电商平台之间确认信息。

彭新宇说，这个环节大约有 260 多步，而且能够覆盖 95% 以上的常见场景。企业可以把这些重复流程整理成标准，让 Agent 负责查询、判断和推进；新的异常则进入下一轮训练。

这个案例重新定义了客服的工作。客服的价值不只在于语气是否友好，还在于能否让客户拿到货、减少投诉，并把内部流程推进到结果。

作者概括：一通电话需要 Agent，是因为企业的答案藏在多个系统和多个动作里，客服必须把这些环节推进到结果。

企业先找最耗人的地方

企业不需要一开始就把所有流程都 Agent 化。彭新宇建议先寻找三类场景：耗人最多的地方，例如电话、投诉和重复查询；耗钱最多的地方，例如赔款止损、营销投放和素材试验；耗时最多的地方，例如客户需要等待数小时甚至数天才能得到答复。

这三类场景有一个共同条件：结果必须具体、能够度量。企业可以比较处理量、等待时长、赔付金额、投放转化率或人力成本，然后判断 Agent 是否真的改变了业务。

对企业来说，多快好省是一组必须说明参照系的指标。只有先说明和谁比、比较什么、用多长时间比较，业务结果才有意义。

AI 实施更像新雇一个员工

传统软件交付后，客户还要自己学习怎样使用。彭新宇把 AI 实施比作新雇一个员工：客服、营销和销售 Agent 进入企业时，已经带着一组岗位能力，企业要做的是给它权限、目标和裁量权。

这个比喻同时提高了企业的要求。企业要说明数字员工可以查看哪些数据、调用哪些系统、审批哪些金额，也要说明什么时候必须交给人处理。权限边界不清楚，Agent 就无法稳定工作。

Agent 上岗以后，企业还要处理异常、复盘表现、分派任务和教它学习新技能。交付不再是项目的终点，持续运营才是数字员工开始产生价值的地方。

数据治理让经验变成工作方法

企业的知识库、基础信息和历史流程如果没有整理，数字员工进入公司后也无法判断下一步做什么。FDE 要把企业上下文变得可查、可用、可授权，这也是 Data for Agent 的实际含义。

瓴羊分享过一个投手案例。同一企业里，最好投手在三个月内做了超过一万次价格调整，普通投手只有一百多次。两种行为的差异很难靠师傅带徒弟完整传递，却可以通过历史数据被观察、比较和建模。

投手的工作包含采集竞品新品和价格、分析数据、做决策、调整策略。数字员工可以把这些动作放入学习、建模、执行、迭代的循环里，再用好坏案例更新下一次判断。

销售 Agent 要把拜访前后串起来

销售流程比投放更依赖行业细节。制造业的渠道销售要规划一天访问哪些客户，准备每次会面的材料，判断交流内容与企业任务的关系，还要把会后任务录入内部系统并触发后续跟进。

在一个制造业案例中，团队从一个表现最弱的省份开始试点。路线规划、会面准备、会后总结和系统录入被连接起来后，彭新宇说，这个省在当年上半年被评为最先进，最终拿到公司的销冠。

瓴羊把企业增长拆成售前、售中和售后。营销、销售、客服和运营构成四类预设岗位，企业自己的数据资产、流程、权限和审批边界则构成 X。预设能力要靠 X 才能在具体企业里工作。

Agent 上岗是一周的逐步放量

企业不会把 Agent 在某一天直接切换到全部流量。一个案例采用一周的上岗流程：第一天先处理客户需求较少的时间段，第二天进入工作高峰并使用全量数据，第三天扩大到八小时，之后继续比较异常、投诉和优于人工的部分。

这套方法让企业看到异常的边界，也让团队逐步形成一个参照系。参照系可以是企业最好的员工，也可以是企业事先设定的业务标准。

FDE 的组织因此需要不断评审和调整。它既要懂岗位，也要懂模型和数据，还要把每一次反馈放回企业的工作流程。

FDE 是组织协作，不是一个全才

彭新宇认为，一个人同时覆盖行业、业务、模型、数据和运营，时间会被切得太碎。更现实的方式是让不同角色组成一个 FDE 组织。

BA 负责业务结果和流程，设定评测标准；AI 架构师把业务问题翻译成模型选择和人机边界；首席岗位专家负责调教 Agent，吸收异常和优秀处理方式。三类角色共同把岗位经验变成可执行的系统。

企业内部的 IT、CIO、CTO 和岗位专家都可以沿着这条路径向业务结果靠近。客服人员的成长也会改变：他们可以从处理一线投诉，转向管理一组客服 Agent，负责异常处理、复盘和任务派发。

商业模式：坐席费和效果费都要落到账上

按坐席或工作量收费

客服场景可以拿原有的人力成本作参照，用相近的服务规模比较投入与原先效果。

按业务效果结算

营销和投手场景可以把转化率、投放结果等指标作为参照，对超过原有人工作法的增长部分进行分成。

合作通常要先做最小价值验证。客户在自己的业务单元和数据单元里体验到结果，再决定是否验收、续费和扩大范围。收费方式可以不同，但比较口径必须稳定。

这也解释了为什么瓴羊不把重点放在为每家企业开发一套专有软件。团队先选择销售、营销、客服等增长场景，再把有共性的部分做成可复用服务。

中国式 FDE 要同时做地基和应用

彭新宇提到，Salesforce、SAP 等信息化系统已经沉淀了不少工作流和数据标准。中国的平台企业也承载了部分 SaaS 能力，但不同企业的数据基础和流程标准差异更大，FDE 往往要从数据治理和流程梳理开始。

中国大型企业普遍有自己的 IT 团队，外部团队要证明自己带来的业务结果。淘宝、天猫、企业微信等平台积累了流量和运营经验，懂这些平台的人更容易把 Agent 放进中国企业的真实工作里。

因此，中美的 FDE 案例不能直接一一换算。两国的企业基础、付费习惯、人才结构和平台环境不同，企业真正要比较的是自己的投入是否换来了可持续的业务结果。

模型选择也要放进企业总账

Agent 系统可以部署在阿里云、公有云或企业自己的环境里。系统部署的位置不等于模型必须私有部署，企业要先判断数据边界、业务需求和成本承受能力。

彭新宇提醒，大尺寸开源模型的参数规模可达 2 点几 TB，私有部署还可能需要几千万级别的初始化投入。对企业来说，先回答是否需要，再回答是否承担得起，比追求最强模型更重要。

模型升级也不能绕过企业验证。团队要比较升级前后的效果，检查流程、权限和管理边界，再决定是否切换。企业要的是稳定的工作输出，模型能力只是实现这个结果的一部分。

作者概括：企业级 AI 的竞争不只发生在模型排行榜上，也发生在数据治理、运营效率和成本核算里。
