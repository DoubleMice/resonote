台前之火 · 2026 年 7 月

43.「26Q2」大模型半年报：RSI，Fable，5.2，混元3，龙猫，到处都是斩杀线

嘉宾：王铁震

AI 研究 模型产品 编程智能体

距离上一期季度复盘只过了三个月，主持人回听时已经觉得许多判断过时了。这种时间感贯穿了整场对谈：模型发布越来越密集，模型公司之外的互联网公司也开始训练大模型，讨论者不愿只用一张能力榜单判断行业。他们想弄清的是，模型怎样继续变强，谁能把能力放进真实任务，以及人还要在循环中承担什么工作。

RSI 是一条有人参与的改进循环

对谈从递归自我改进开始。王铁震用编译器自举解释这个词：第一版编译器由更早的工具或人写出，之后编译器可以用自身语言继续编译和迭代。放到大模型上，系统先由人训练到足够可用，再让模型参与改进工具、推理流程、训练方法或某项性能指标。Auto research 是让模型围绕外部目标反复尝试；RSI 则进一步让这种尝试反过来改善系统自身。

这个比喻也划出了边界。模型在封闭循环里持续改代码，项目的复杂度会不断累积。到了某个阶段，模型的上下文窗口、局部理解和验证能力都不足以覆盖整个系统，新的修改可能修复眼前问题，也可能碰坏另一处。系统需要从外部得到新的实验结果、任务数据和人类判断，才能避免沿着旧路径打转。

对谈没有把机器写了多少行代码视为自主程度的充分证据。模型可以生成大量实现细节，而工程师仍在逐条规定目标、范围和验收方式。判断控制权时，需要追溯关键决策是由谁作出的。

因此，人和模型的分工会转移，不会简单地消失。人类负责把复杂目标抽象成架构、模块边界和不变量；模型在这些边界内完成局部实现、测试和重复劳动。当设计在新场景失效时，人再重新审视抽象，把新的限制和偏好交给模型。这套工作方式比把任务整包交出去更适合长期维护的软件。

从许愿式开发回到可维护的系统

王铁震把一种常见体验称为许愿式开发：用户描述一个结果，模型很快交出看似可用的项目，用户却不知道内部发生了什么。这对一次性工具很有效。若只需在少数场景运行，使用者不必掌握每个模块，也不一定在意代码是否整洁。

长期服务面对的是另一种问题。项目一层层增加功能后，维护者可能无法判断模型改动会影响哪些地方。模型当前版本也未必能管理已经堆高的代码库，于是团队等到更强模型发布，再请新模型重构旧系统。这种接力有时能解决问题，却没有自动建立起可预测性。

他正在做的自举实验把这件事拆成几段。首先，让 GLM-5.2 为自己生成可使用的 Harness；现有 Claude 在其中承担带领和校验的角色。接下来尝试把 GLM-5.2 的推理环节也接进去，之后再从 LoRA 等计算量较小的训练入手。实验目标先是跑通自举链路，再讨论怎样提高某个性能。工具、推理和训练的每个环节都应能被观察和修正；这项实验的范围仍限于这条链路。

这个实验还带出一个能力限制。模型能处理训练语料里已经出现过、或能借由已有方法拼接出来的任务。例如，给定明确文件和线索后，模型可能找出相似的漏洞；给定已知接口，它也能搭出一个基础 Harness。面对缺少先例的新方向，模型往往缺少选择路径的依据。对谈把 research taste 放在这里：研究者需要判断何时值得投入算力和试验，哪怕现有语料提供的大多是反对理由。

真实交互正在变成模型的训练来源

主持人提到 OpenAI 的 record and replay：用户录下修改简历、筛选简历等过程，系统再尝试完成相似操作。这类交互的价值不在录屏本身，而在它保留了完整任务如何开始、用户怎样操作、哪里作出反馈。王铁震把未来产品的方向分成两部分：尽量收集对模型有用的人类交互，再把模型能力下发到尽可能多的场景。

一名用户在某个工作流里发现有效方法，另一名用户可能在下一版模型中直接获得相近能力。模型厂商若把这些实践纳入训练，就会把分散在不同人手里的经验重新分发。这个过程解释了模型为何会在某些任务上突然变得更好，也提醒人们，模型的进步常常吸收了外部世界已经产生的做法。

交互数据

真实任务、用户修正和结果反馈，比脱离场景的文本更接近可训练的工作过程。

隐私边界

语音转写、屏幕操作和应用上下文涉及大量私人信息，收集与使用必须有清晰的条件。

本地选择

把模型放在设备上运行未必追求最高能力，也可能是为了减少持续上传和订阅依赖。

对谈没有把云端服务描述成唯一道路。王铁震设想过一种装好模型与应用的本地智能设备。它未必比云端模型更强，但对重视私密性、并且长期使用的人，购买设备后在本地运行可能是另一种成本结构。便利、能力规模和隐私保护各有代价，不能用同一个数字排出高低。

Harness 的难点从能用转向好用

Harness 是模型和执行环境之间的工具层。两年前，开发一个可调用模型、执行命令、返回结果的基础 Harness 仍较困难；今天，相关做法已经出现在论文、开源项目和讨论帖里，模型见过足够多的例子后，可以按接口搭出基本形态。对谈认为，真正难的部分转到了用户体验。

终端界面对模型友好，因为模型可以运行工具、读取文字结果、再尝试下一步。复杂图形界面有动画、拖拽和大量边缘状态，模型很难自己获得足够可靠的反馈，开发者就得亲自充当测试人员。成熟的工具不只执行任务，还要让人能看见模型打算做什么、及时确认并撤回风险操作。

安全设计也因此成为 Harness 的一部分。节目提到 Claude Code 会用安全小模型检查命令，Codex 使用 sandbox；王铁震自己的做法是先检查命令，再放入 Docker 运行。不同产品可以采用不同方案，工具生态也未必收敛为唯一赢家。不过，愿意持续打磨交互、兼容场景和安全边界的头部产品，仍可能得到更广泛的使用。

Fable 与开源斩杀线

谈到 Fable，主持人最初把它的发布氛围理解为一次接近国家安全级别的能力跃迁。王铁震的判断更克制。他承认，能够在海量目标中主动发现 0day 漏洞需要更强的搜索范围、针对安全领域的训练与更高能力；但当问题被局部化、文件和线索已被给出时，开源模型也可能找出相似漏洞。

这让讨论回到产品差异的来源。安全攻击语料、模型尺寸、系统搜索能力和发布叙事，都可能拉开结果。王铁震不认为 Fable 已经采用与现有模型完全不同的范式。他认为，开源模型的能力线正在上升，闭源产品若只与它们相近，就需要不断证明自己在哪些任务上能提供更高的价值。

开源的影响不止于价格。公开权重、技术报告和架构探索把共同的 checkpoint 往前推，后来者可以站在此处继续使用自己的数据微调。对研发而言，这降低了参与门槛；对投资而言，问题更尖锐：当多个模型的能力接近，第一名之外的厂商怎样维持价格和利润？

开放基线

更多团队可以获得可用模型，围绕自己的任务继续开发。

商业分化

模型能力之外，数据、工具体验、服务成本与行业场景需要承担更多差异化任务。

美团与腾讯：训练工程和数据入口

龙猫 2.0 让主持人感到意外的地方，不只是美团也做了模型。节目描述它是一个 1.6T 模型，在 5 万卡的国产卡集群上训练。王铁震把重点放在训练工程：推理和训练面临的约束不同，后者是长程任务，涉及大量语料、卡间通信、数值精度与底层软件适配。完全不依赖 N 卡完成这样的训练，被他视为很有分量的工程成果。

模型能力也会改变大厂采购外部 API 的条件。若一家公司拥有能覆盖内部任务的模型，它不必为一般能力购买服务；外部模型需要在具体任务上明显更好，才有购买理由。另一方面，应用中的专有数据又让这些公司更想把模型留在产品内部。主持人以点评场景举例：找商场里安静、有空位的咖啡店，需要商户、位置、评价等相互关联的数据，通用助手未必能够拿到。

混元 3 的讨论把目光放到数据清洗与训练方法。王铁震观察到，混元 3 相比 Preview 的模型结构没有变化，却出现明显性能提升。他据此推测，训练数据和训练方法在这次提升中很重要；同时他也承认，研究团队会掌握更多消融实验，外部体验者无法只凭发布结果分开所有变量。

腾讯的特殊位置在于它拥有多个高频产品入口：微信、腾讯会议、WorkBuddy 等应用都会产生交互。数据量不等于训练价值，聊天内容与完成复杂任务后得到的反馈，价值并不相同。更重要的是，涉及个人沟通的数据必须在隐私保护和合法使用的前提下才可能进入模型改进。模型公司和产品公司的竞争，正在落到怎样获得、清洗、使用并保护这些数据上。

Coding 的外延正在变成自动化

对谈最后回到 coding。王铁震认为，代码生成有直接的商业价值：软件工程师的工作时间昂贵，模型若能承担一部分任务，就能立即进入预算。更重要的是，代码是许多数字化工作的实现层。制作网页、生成报告、操作表格、完成前端设计，最后都可能落到软件执行。

主持人更愿意把这件事称为自动化。未来的使用者未必把自己看作程序员；他们只是用自然语言提出需求，让系统完成可以被软件描述的工作。编译是否通过、测试是否成功、输出是否符合预期，又为模型提供了连续反馈。这种可执行、可验证的闭环，解释了为什么各家模型公司把 coding 放到优先级前列。

二季度的讨论最终没有给出永久排名。它留下了一组更实际的问题：模型能否持续获得算力和高价值反馈数据，Harness 能否把能力变成可靠体验，大厂的数据入口能否在合规条件下产生训练收益，以及模型能力接近后，哪些产品仍值得用户付费。下一季度的发布会继续改写答案，但这些问题不会因为榜单更新而消失。
